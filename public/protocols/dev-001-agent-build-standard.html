DEV-001 Agent Build Standard Protocol

Department: DEV (Development) Version: 1.0 Created: 2026-05-25 Owner: Lumina Status: DRAFT

Purpose

Build a new agent with proper structure, testing, security, and documentation. Every agent follows the same architecture pattern so that any agent can be understood, debugged, and modified without tribal knowledge.

Trigger

  • When building a new agent or automated system
  • When significantly upgrading an existing agent (new major version)

    • Prerequisites

  • Agent purpose defined (what problem does it solve?)
  • Data sources identified (what does it read?)
  • Output format defined (what does it produce?)
  • Schedule defined (when/how often does it run?)

    • Steps

    Step 1: Requirements Document

    Write a short requirements doc BEFORE coding: 
    markdown

    Agent: [Name]
    
Purpose: [1-2 sentences]
Department: [RSC/DEV/RPT/DSN/OPS/STR]
Protocols: [Which protocols does it follow?]
Data Sources: [Where does it get data?]
Output: [What does it produce and where?]
Schedule: [When does it run?]
Security Level: [LOW/MEDIUM/HIGH based on Lethal Trifecta audit]
Human Oversight: [HITL — needs approval / HOTL — autonomous with monitoring]

    Step 2: Architecture Design

    Follow the Agentic Mesh pattern (Broda):
  • Identity: Agent has a name, version, and capability profile
  • Discovery: How does this agent find data/sources/other agents?
  • Trust: What validation does it apply to inputs?
  • Transactions: What does it exchange with other systems?
  • Oversight: Where does the human-in-the-loop checkpoint sit?

    • Step 3: Lethal Trifecta Security Audit

    Before writing ANY code, answer: 1. Does this agent access private data? (Yes/No) 2. Does this agent process untrusted content? (Yes/No) 3. Does this agent make external calls? (Yes/No)

    If YES to all three → HIGH security. Requirements:

  • Sandboxed execution environment
  • Input validation and sanitization
  • Rate limiting on external calls
  • Output filtering before publishing
  • Guardrails on what actions it can take
  • Human approval for HIGH-impact decisions

    • If YES to two → MEDIUM security. Requirements:

  • Input validation
  • Error handling with safe defaults
  • Logging of all external interactions

    • If YES to one or none → LOW security. Requirements:

  • Standard error handling
  • Basic logging

    • Step 4: Implementation

    Follow the standard agent structure: 
    python
#!/usr/bin/env python3
"""
[Agent Name] — V[Version]
Purpose: [1-2 lines]
Protocols: [Which protocols this agent follows]
"""
    === PARAMETERS ===
    

    All tunable parameters at the TOP of the file, clearly labeled
    === DATA SOURCES ===
    

    All file paths, API endpoints, keys referenced from config
    === CORE LOGIC ===
    

    Main processing functions
    === OUTPUT ===
    

    What gets produced and where it goes
    === LOGGING ===
    

    Structured logging of actions taken
    === ENTRY POINT ===
    
if __name__ == '__main__':
    main()

    Code quality rules:

  • Every function has a docstring
  • Every external call has error handling
  • Every data source has validation (check it exists, check format)
  • No hardcoded secrets (use config/api-keys.env)
  • No model fields in cron jobs (lesson from May 19 cascade)

    • Step 5: Testing

    Before first deployment: 1. Dry run: Execute with --dry-run flag that shows what it WOULD do without doing it 2. Small batch: Run on 1-3 items, verify output 3. Full run: Run on full dataset, verify output 4. Edge cases: Test with missing data, bad format, empty input, timeout 5. Live verification: Check the output is accessible (live URL, file exists, dashboard loads)

    Step 6: Cron Job Setup (if scheduled)

    Follow DEV-003 (Cron Job Creation):
  • No model field in payload (HARD RULE)
  • Explicit delivery channel (telegram/discord)
  • Appropriate timeout (default 300s, increase for long tasks)
  • Test by running manually first, then create cron

    • Step 7: Documentation

    Create agent record in AGENTS.md: 
    markdown
| Agent Name | Role | Status | Protocols | Security Level | Last Active |
|------------|------|--------|-----------|----------------|-------------|
| [name] | [role] | 🟢/🟡/🔴 | [protocol IDs] | LOW/MED/HIGH | [date] |

    Step 8: Deployment Verification

    After deployment: 1. Check the agent ran successfully (no errors in log) 2. Check output is accessible (live URL, file exists) 3. Check output is correct (spot-check data values) 4. Check cron is running (if scheduled) 5. Report status to Roo

    Quality Gates

    Requirements doc written before coding
    Lethal Trifecta audit completed
    Security level assigned and appropriate safeguards in place
    Dry run + small batch + full run + edge cases tested
    No hardcoded secrets
    No model fields in cron payload
    Agent registered in AGENTS.md
    Live verification completed

    Error Handling

    | Error | Response | |-------|----------| | Agent fails on first run | Check logs, fix, re-test from Step 5 | | Security audit reveals HIGH risk | Add safeguards BEFORE deploying, don't skip | | Data source unavailable | Agent should log error and exit gracefully, not crash | | Output doesn't match expected | Revert to backup, investigate, fix, re-test |
