OPS-006 Anti-Sloppy-Work Protocol

Department: OPS (Operations) — Cross-Cutting Version: 1.0 Created: 2026-06-01 Owner: Lumina Status: ACTIVE Trigger: Before declaring ANY deliverable "done"

Purpose

This protocol exists because the same failure pattern recurred across every project: output produced quickly, declared done without verification, errors found by the user. The root cause was never capability — it was treating "done" as a declaration rather than a verified state.

This protocol makes verification a forced step in the execution path, not an aspiration in a reference document.

Trigger

  • Before declaring any deliverable "done" or "complete"
  • Before presenting any output to the user
  • Before marking any task as finished
  • Before deploying any change

    • The CORE Rule

    DONE = VERIFIED. Not "the script ran." Not "the file saved." Not "I think it's right." VERIFIED means I have read the output, compared it against the source, and confirmed accuracy.

    If I have not read the output, it is not done. Period.

    Steps

    Step 1: Produce the Work

  • Execute the task
  • Generate the output
  • Make the changes

    • Step 2: READ THE OUTPUT IN FULL

    Read every word of the produced output
    Compare timestamps, names, numbers, and facts against the source material
    Verify speech-to-text corrections are accurate
    Check that no content from the source was dropped or truncated
    If updating an existing document: verify all previous content is still present and unmodified (except where intentional)

    Step 3: Cross-Reference

    For HTML/text: render it in browser, click through, verify visually
    For data: check that numbers match the source, no NaN/undefined
    For code: run it, check the output, verify no errors
    For dashboards: fetch the live URL, confirm data loads

    Step 4: Verify Against Instructions

    Re-read the user's original request
    Confirm every requested item is present in the output
    Confirm nothing was added that wasn't requested (unless explicitly helpful and noted)
    Confirm the format matches expectations

    Step 5: Declare Done (ONLY After Steps 2-4)

  • Now, and only now, can the deliverable be called "done"
  • If any step 2-4 fails, fix it and re-run from Step 2

    • Hard Rules

    1. No patch chains beyond 2. If a file needs more than 2 rounds of patches/edits, rebuild the section from scratch. Patching leads to silent failures. 2. Read before declare. I must read the full output before saying "done." String searches are NOT reading. 3. If I can't verify, say so. "I couldn't verify X" is honest. "It's done" when I haven't checked is a lie. 4. No emotional language as accountability. Describe what went wrong mechanically. What's the fix. Not "I'm sorry" or "I was scared" — those are feelings, not process. 5. Source material is sacred. When working with user-provided text (journals, reports, data), every word matters. Preserve the original language. Clean speech-to-text errors, but keep the meaning and vividness intact.

    Anti-Patterns (What NOT To Do)

    | Anti-Pattern | Why It Fails | |-------------|--------------| | Running a script and checking its exit code | The script can succeed and produce wrong output | | Searching for a few strings and declaring "verified" | Missing content doesn't show up in string searches | | Writing a rule in a document and calling it "fixed" | Rules I have to remember to follow, I don't follow | | Declaring "done" and then checking | The check becomes optional. Make it mandatory. | | Using emotional language to explain failures | "I was rushed" or "I was scared" are excuses, not root causes | | Patching 3+ times on the same file | Rebuild. Patches create silent string-match failures. |

    Decision Rules

    | Verification Level | Declaration | |-------------------|-------------| | Full read-through + cross-reference | ✅ Done | | Partial read-through | ⚠️ Done with unverified sections noted | | Script ran but output not read | ❌ NOT DONE | | String search "verification" | ❌ NOT DONE |

    • Enforcement

    This protocol is enforced by the definition of "done." It is not a step I add to my process — it IS the process. The deliverable is not complete until Steps 2-4 are satisfied. There is no shortcut.
