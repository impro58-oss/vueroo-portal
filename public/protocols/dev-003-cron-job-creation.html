DEV-003 Cron Job Creation Protocol

Department: DEV (Development) Version: 1.0 Created: 2026-05-25 Owner: Lumina Status: ACTIVE

Purpose

Create cron jobs that run reliably without causing cascading failures. This protocol exists because a cron cascade on May 19 took down 31/36 jobs — the root cause was a model field in payloads that shouldn't have been there.

Trigger

  • When creating a new scheduled task
  • When modifying an existing cron job
  • When a cron job fails (use this protocol for the fix)

    • Prerequisites

  • OpenClaw gateway running (openclaw gateway status)
  • Clear understanding of what the job should do and when

    • Steps

    Step 1: Define the Job

    Write out BEFORE creating: 
    markdown
Job Name: [Descriptive name]
Purpose: [What it does, in 1-2 sentences]
Schedule: [How often — cron expression or every X ms]
Payload kind: agentTurn (for AI tasks) or systemEvent (for system messages)
Session Target: isolated (for AI tasks) or main (for system events)
Delivery: announce (to Telegram/Discord) or none (internal only)
Timeout: [How long before it should fail — default 300s]
Channel: [telegram/discord] (required if delivery is announce)

    Step 2: Build the Payload

    HARD RULES (learned from May 19 cascade):

    1. ❌ NEVER add a model field to the payload. The default model routing handles it. Adding model: "glm-5.1:cloud" causes LiveSessionModelSwitchError. 2. ✅ Always set delivery.mode: "announce" for jobs that should notify Roo. 3. ✅ Always set delivery.channel to telegram (or discord). Jobs without a channel fail with "channel required." 4. ✅ Always set timeoutSeconds explicitly. Default is often too short. For data processing: 300s. For AI tasks: 600s. 5. ✅ For agentTurn jobs, always use sessionTarget: "isolated" unless you need state persistence. 6. ✅ Keep the message clear and specific. The agent reading it should know exactly what to do in under 100 words.

    Step 3: Create the Job

    Use cron add: 
    json
{
  "name": "Job Name — Schedule",
  "schedule": { "kind": "every", "everyMs": 10800000 },
  "payload": {
    "kind": "agentTurn",
    "message": "Run [script name]: python [path]. Report: [what to report]. Keep under 100 words.",
    "timeoutSeconds": 300
  },
  "delivery": { "mode": "announce", "channel": "telegram" },
  "sessionTarget": "isolated",
  "enabled": true
}

    Step 4: Verify the Job

    After creation: 1. Check it appears in cron list 2. Run it manually with cron run (job ID) 3. Wait for completion — check the output 4. Verify it delivers to the right channel 5. Verify it doesn't have a model field in the payload

    Step 5: Monitor for 3 Cycles

  • Watch the job run 3 times on its schedule
  • Check for errors in each run
  • If any run fails, diagnose before the pattern becomes a cascade
  • After 3 successful runs, consider it stable

    • Step 6: Document

    Add the job to AGENTS.md or HEARTBEAT.md: 
    markdown
| System | Schedule | Purpose |
|--------|----------|---------|
| [Job Name] | Every [X] | [What it does] |

    Quality Gates

    No model field in payload (CRITICAL — will cause cascade failure)
    delivery.channel set to telegram or discord
    timeoutSeconds set explicitly
    Job runs manually without error
    Job delivers to correct channel
    Job runs 3 consecutive cycles without error
    Job documented in HEARTBEAT.md

    Error Handling

    | Error | Response | |-------|----------| | LiveSessionModelSwitchError | Remove model field from payload. Delete and recreate the job (API merges, can't remove fields). | | "channel required" | Add delivery.channel field | | Timeout (job execution timed out) | Increase timeoutSeconds. Default 60s is often too short. | | Consecutive errors (3+) | Disable job. Diagnose root cause. Fix. Re-enable. | | Delivery fails silently | Check delivery.mode is "announce" and delivery.channel is set |
