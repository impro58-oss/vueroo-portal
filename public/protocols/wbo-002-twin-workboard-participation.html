Purpose

Twins are not passive task recipients. They are active board participants — accountable for their own progress, their own improvement, and their contributions to the board. This addendum defines how twins interact with the workboard as first-class members.

Twin Boards

Each twin gets their own board namespace for personal projects, sidebars with Roo, and individual accountability:

Board ID Owner Purpose
Lumina Operations lumina-ops Lumina System-wide COO work, recurring maintenance, cross-twin coordination
Alex Workspace alex-ws Alex Growth projects, Hormozi domain work, sidebar projects with Roo
Thiel Workspace thiel-ws Thiel Strategy projects, Thiel domain work, sidebar projects with Roo

Avaark Board avaark Shared Cross-twin project work (Snodo, ComplyKeep, Avaark, Sōl)

How Twins Use Their Boards

  1. Capture their own ideas — twins create cards on their own board when they think of something that needs doing
  1. Track their own progress — twins move cards through the lifecycle themselves
  1. Sidebar projects with Roo — when a twin works on a 1:1 project with Roo, the work is tracked on the twin's personal board with cards
  1. Cross-twin collaboration — cards on the avaark board for shared project work, each card assigned to the responsible twin

Twin Card Creation Authority

Twins can create cards on:

  • ✅ Their own workspace board (<twin>-ws)
  • ✅ The shared Avaark board (avaark) — for cross-twin project work

Twins CANNOT create cards on:

  • ❌ lumina-ops — that's Lumina's board
  • ❌ Other twins' workspace boards

Accountability Structure

Weekly Self-Review

Every Sunday, each twin creates a self-review card on their own board:

Title: Weekly Self-Review — Week of [date]
Status: todo → running → done
Notes:
- What I accomplished this week (list cards completed)
- What I learned (from learning queries, research, web searches)
- What I'm stuck on (blocked cards, open questions for Roo)
- What I want to work on next week (proposed new cards)
- Am I earning my keep? (honest self-assessment — yes/no/needs improvement + why)

Lumina reviews all 5 self-reviews on Sunday evening during the nightly sweep and flags any concerns to Roo.

Proof Requirements

Every done card must have proof attached. Acceptable proof:

Work Type Proof
NotebookLM query Note ID saved inside notebook + brain note file path
Research File path to research output + key findings summary
Code/build Live URL verification or test output
Writing/content File path to document
Decision/recommendation File path to recommendation doc + decision logged in DECISION-LOG.md

Cards without proof get flagged by diagnostics (missing_proof) and Lumina sends them back to review.

Stale Card Rules

If a twin has cards that haven't been updated:

  • 7 days stale → Lumina comments on the card asking for status
  • 14 days stale → Lumina flags to Roo in weekly summary
  • 30 days stale → Card archived, twin asked to explain

Backup — Workboard History

What Gets Backed Up

The workboard SQLite database at ~/.openclaw/plugins/workboard/workboard.sqlite contains all boards, cards, labels, events, comments, proof, artifacts, and history. This is irreplaceable operational data.

Backup Strategy

  1. Daily mirror — the existing D:\Lumina Carbon Copy Sync (2:30 AM IST) already mirrors the entire .openclaw directory including the workboard database. So the workboard is already being backed up nightly to D:.
  1. Weekly snapshot — when the weekly snapshot rotation task runs (workboard task #1), the workboard database is included in the snapshot. This gives rollback points.
  1. Weekly export — every Sunday during the nightly sweep, Lumina runs a full card export to JSON as a human-readable backup:
    2.    openclaw workboard list --include-archived --json > board/workboard-export-YYYY-MM-DD.json

This file goes into the vault and gets synced to D: on the next mirror.

  1. DECISION-LOG.md — all board decisions are already logged in the append-only board/DECISION-LOG.md. This is the human-readable audit trail that survives even if the database is lost.

Recovery

If the workboard database is corrupted or lost:

  1. Restore from D:\Lumina mirror (latest = last night)
  1. If mirror is also bad, restore from weekly snapshot
  1. If snapshots are bad, reconstruct from the JSON exports in board/
  1. DECISION-LOG.md provides the audit trail regardless

Communication Map

Roo ←→ Twin (Telegram DM or office group) — strategic discussions, decisions
Roo ←→ Lumina (webchat/Telegram) — system direction, approvals
Lumina → Twin (workboard dispatch) — task assignment
Twin → Lumina (sessions_send) — task requests, escalations
Twin → Twin (sessions_send or office group) — collaboration requests
Lumina → Roo (webchat/Telegram) — escalations, blocked work, weekly summary
Twin → Board (self-created cards) — self-initiated work, sidebar projects

Twin Onboarding Checklist

When a new twin is activated:

  • [ ] Twin reads board/twin-workboard-briefing.md
  • [ ] Twin reads this protocol (memory/protocol-wbo-002-twin-workboard-participation.md)
  • [ ] Lumina creates the twin's workspace board (<twin>-ws)
  • [ ] Twin creates their first card: "Self-introduction and first-week plan"
  • [ ] Twin confirms understanding of card lifecycle, proof requirements, and learning cycle
  • [ ] Lumina adds twin to the avaark board if they're working on shared projects
