OPS-002 Incident Response Protocol

Department: OPS (Operations) Version: 1.0 Created: 2026-05-25 Owner: Lumina Status: DRAFT

Purpose

When something breaks, follow this process. No panic, no guessing, no "just restart it and hope." Diagnose → fix → verify → document.

Trigger

  • A system or agent fails
  • A cron job reports errors
  • A dashboard is down
  • Data pipeline produces wrong output
  • Roo reports something broken

    • Steps

    Step 1: Don't Touch Anything Yet

    Before fixing, UNDERSTAND: 1. What exactly is broken? (Be specific: "NeuroVue dashboard returns 404" not "NeuroVue is broken") 2. When did it break? (Check last known good state) 3. What changed? (Recent deployments, config changes, API changes) 4. How bad is it? (1 user affected vs. all systems down)

    Step 2: Diagnose

    Run these checks IN ORDER: 1. Is the service running? Check process/port 2. Is the data present? Check file existence and size 3. Is the data valid? Check for NaN, empty, corrupted 4. Is the network working? Check connectivity, DNS, firewall 5. Are dependencies up? Check APIs, databases, external services 6. Check logs. What errors appear in the last hour?

    Step 3: Classify Severity

    | Severity | Definition | Response Time | Example | |----------|-----------|---------------|---------| | CRITICAL | Revenue-producing system down, data loss risk | Immediate | Trading system placing wrong orders | | HIGH | Key system down, no workaround | <30 min | Dashboard completely offline | | MEDIUM | Degraded but functional, workaround exists | <4 hours | Some data stale, dashboard partially broken | | LOW | Cosmetic, minor inconvenience | Next maintenance | Formatting issue, stale cache |

    Step 4: Fix

    Rules for fixing: 1. Backup before changing (copy the current broken version somewhere) 2. Fix the root cause, not the symptom (don't just restart — find WHY it crashed) 3. Make the smallest change that fixes it (don't refactor while fixing) 4. Test the fix before declaring it fixed (follow DEV-002 Code Quality Gates) 5. If you can't fix in 30 minutes, escalate to Roo with a clear summary

    Step 5: Verify

    After applying fix: 1. System is running? ✅/❌ 2. Data is correct? ✅/❌ 3. No new errors? ✅/❌ 4. Dashboard loads? ✅/❌ 5. Cron job runs on next cycle? ✅/❌

    Step 6: Document

    Write to .learnings/ or incident log: 
    markdown

    YYYY-MM-DD: [Incident Title]
    

  • Severity: CRITICAL/HIGH/MEDIUM/LOW
    • 

  • Duration: [how long it was broken]
    • 

  • Root Cause: [the ACTUAL cause, not just "it crashed"]
    • 

  • Fix Applied: [what you did]
    • 

  • Verification: [how you confirmed it's fixed]
    • 

  • Prevention Rule: [what rule/protocol prevents this happening again]
    •

    Step 7: Prevention

  • Add the prevention rule to the relevant protocol
  • Add a check to health monitoring if applicable
  • If this is a recurring pattern, flag for architectural fix

    • Quality Gates

    Root cause identified (not just symptom)
    Fix applied and verified
    Incident documented in .learnings/
    Prevention rule added to protocol or monitoring

    Error Handling

    | Situation | Response | |-----------|----------| | Can't diagnose in 15 min | Escalate to Roo with what you know | | Fix makes it worse | ROLLBACK immediately, then diagnose | | Root cause unclear | Stabilize (restart/rollback), then investigate offline | | Multiple things broken | Fix CRITICAL first, then HIGH, etc. |
