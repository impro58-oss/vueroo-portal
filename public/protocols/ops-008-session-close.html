OPS-008 — Session Close Protocol

Department: OPS (Operations)

Version: 1.0

Created: 2026-07-08

Owner: Lumina

Status: ACTIVE

Trigger: "protocol close" spoken by Roo, or end of session, or before gateway restart

Purpose

Ensure every session ends with a structured, durable record that survives memory wipes, context clearing, and gateway restarts. This protocol exists because session close was previously done from memory of past session logs — which is unreliable and fails when memory is wiped.

This protocol is the single source of truth for how to close a session. Do not reconstruct the procedure from session logs. Read this file. Run it.

Prerequisites

  • Session has produced at least some work (if nothing was done, note that and exit)
  • session_status available for runtime metrics
  • Write access to memory/session-logs/

Steps

Step 1: Capture Session Metadata

Run session_status to get:

  • Model used
  • Token count (in/out)
  • Session duration
  • Context usage

Record:

  • Session start time (approximate, from first message)
  • Session end time (now)
  • Protocol(s) used during session
  • Roo's key instructions/decisions

Step 2: Execute the 4-Stage Review

Stage 1: PLAN (Recap)

  • What problem were we solving?
  • What were the success criteria?
  • What constraints applied?

Stage 2: EXECUTE (Summary)

  • What was actually done? (bullet list of concrete actions)
  • What files were created/modified/deleted?
  • What cron jobs were added/removed?
  • What database changes were made?
  • Progress notes: deviations, discoveries, adjustments

Stage 2.5: VERIFY

  • [ ] Does the work exist in the real environment? (not just "the command ran")
  • [ ] Are all claims verified against source files?
  • [ ] No regressions? (existing systems still work)
  • [ ] If you can't verify something, write EXACTLY what's unverified and why
  • If deliverables exist: run appropriate verification (read file, check size, run test)

Stage 2.6: SCAFFOLD REVIEW

  • Was the protocol used fit for purpose?
  • Was the pre-execution plan accurate?
  • What worked well in the approach?
  • What failed or was awkward?
  • Should any protocol be updated? (if yes, note specific change)
  • What would I do differently next time?

Stage 3: REVIEW (Quality)

  • Does this solve the original problem?
  • Are there bugs or unresolved issues?
  • Is documentation complete?
  • Confidence level (HIGH/MEDIUM/LOW) with reasoning

Stage 4: DOCUMENT (Persist)

Write the session log to: memory/session-logs/YYYY-MM-DD-session-log-<topic>.md

Required sections in the session log:

  1. Header: Session date/time, agent, model, protocol, status
  1. Stage 1: PLAN — Problem, success criteria
  1. Stage 2: EXECUTE — What was done, files created, cron changes, DB changes
  1. Stage 2.5: VERIFY — Verification checklist with actual results
  1. Stage 2.6: SCAFFOLD REVIEW — What worked, what failed, protocol update proposals
  1. Stage 3: REVIEW — Quality check, issues found, confidence level
  1. Stage 4: DOCUMENT — Files created, key findings, decisions, next steps
  1. Key Decisions — Any decisions that affect future work
  1. Next Steps — What should happen next (for the next session or cron)

Step 3: Update HEARTBEAT.md

If the session changed system state (new cron jobs, new files, DB changes, config changes), update HEARTBEAT.md:

  • Add/update relevant system entries
  • Update "Last Check-in" timestamp
  • Note any new active systems or status changes

Step 4: Update MEMORY.md (if priorities changed)

If the session changed what's being worked on:

  • Update current priorities list
  • Add new memory file references if created
  • Update search hints if new topic areas were opened

Step 5: Identify Unfinished Work

If any work is incomplete:

  • Write a handoff file: memory/handoff-<topic>.md
  • Include: current state, what's done, what's next, important context, files modified, blockers
  • Reference the handoff file in the session log's "Next Steps" section

Step 6: Cron Check

If the session set up automated work (cron jobs):

  • List the jobs created/modified
  • Confirm they are enabled
  • Note the next run time
  • Ensure they have proper delivery mode set
  • Ensure they will self-replicate if part of an ongoing cycle

Step 7: Final Output to Roo

Present a concise summary:

  • What was accomplished (2-3 bullets)
  • What's still pending (if anything)
  • What automated work continues after close
  • Any issues that need Roo's attention
  • Session log file path

Keep it brief — Roo doesn't need the full log, just the bottom line.

Quality Gates

  • [ ] Session log written to memory/session-logs/
  • [ ] Session log contains all required sections (1-9)
  • [ ] Verification checklist completed (not skipped)
  • [ ] HEARTBEAT.md updated if system state changed
  • [ ] MEMORY.md updated if priorities changed
  • [ ] Handoff file written if work is incomplete
  • [ ] Cron jobs confirmed enabled if set up
  • [ ] Final summary delivered to Roo

What NOT to Do

  • Do NOT reconstruct the close procedure from session logs. Read THIS file.
  • Do NOT skip verification. Even if you think it's fine, run the checks.
  • Do NOT skip the scaffold review. This is how the system learns.
  • Do NOT write a vague session log. Include specific file paths, cron job IDs, DB changes.
  • Do NOT declare done without checking files exist. Read the output, don't trust the summary.
  • Do NOT forget to mention unfinished work. Write a handoff file.
