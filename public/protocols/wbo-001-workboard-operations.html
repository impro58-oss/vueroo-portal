Purpose

This protocol defines how Lumina uses the OpenClaw Workboard as the single source of truth for all operational work — system maintenance, twin coordination, knowledge management, and recurring tasks. The workboard replaces holding tasks in memory (which causes context bloat and timeouts).

Board Structure

Future boards created as needed (e.g. avaark-build, snodo-launch).

Card Lifecycle

The full Kanban flow. Each card moves left to right:

triage → backlog → todo → scheduled → ready → running → review → blocked → done

Status definitions:

Status Meaning When to use
triage Just captured, not yet scoped Quick ideas, things to evaluate
backlog Scoped but not time-bound "Someday" work, nice-to-haves
todo Ready to work, no specific time Pick up during work blocks
scheduled Has a specific time window Nightly sweeps, weekly tasks, timed events
ready Dependencies met, waiting for dispatch Cards that need a worker (twin or subagent)
running Actively being executed Someone is working on it right now
review Work complete, needs verification Done but not yet verified by Lumina
blocked Cannot proceed, needs input Waiting on Roo, waiting on auth, etc.
done Complete and verified Nothing more to do

Priority Levels

Priority Meaning Examples
urgent System down, data loss risk Gateway crashed, backup failed
high Blocking other work or causing issues Memory search timeouts, extraction blocked
normal Important but not blocking Brain note synthesis, twin notifications
low Nice to have, do when quiet Cron cleanup, cosmetic fixes

How Lumina Uses the Board

Card Creation Rules

  1. Every task gets a card. If it's worth doing, it's on the board. Nothing lives only in my head.
  1. Notes are self-contained. A card's notes must contain enough detail that I can execute it without remembering context. Include: what to do, where files are, what commands to run, what success looks like.
  1. Labels are for filtering. Use consistent labels: backup, memory, knowledge, coo, twins, cron, telegram, notebooklm.
  1. Position is for ordering. Lower position = higher in the queue within the same priority.

When to Use Each Status

Situation Status Example
I capture a task during conversation triage → scope it → todo "Fix the Telegram duplicate cleanup cron"
Task has a specific time window scheduled "Nightly sweep at 2AM", "Weekly snapshot Sunday"
Task is ready for a twin/subagent to execute ready "Alex: run 3 NotebookLM queries"
I'm actively working on it running I claim it, work it, heartbeat if long
Work done but needs my verification review Subagent finished extraction, I need to check quality
Can't proceed without Roo blocked "Need Roo's Telegram user ID for allowlist"
Verified complete done Extraction confirmed, brain notes written, quality checked

Claiming and Executing

When I start working a card:

  1. Move to running (claim it)
  1. Execute the work
  1. If long-running, heartbeat to keep the claim alive
  1. When done, move to review
  1. Verify the work (read the output file, check the result)
  1. If verified → done with proof (file path, command output, confirmation)
  1. If failed → blocked with reason

Recurring Tasks

For tasks that repeat (nightly sweep, weekly learning, weekly snapshot):

  1. Create the card with scheduled status and full instructions in notes
  1. When the time window arrives, move to running
  1. Execute
  1. Move to done with proof
  1. Immediately create the next iteration as a new scheduled card with the same instructions, updated date
  1. The old card stays done (history), the new card carries forward

This is how recurring work cycles without cron jobs bloating the registry.

Dispatch (for twin work)

When a card needs a twin to do work:

  1. Create the card assigned to the twin's agentId (e.g. agentId: "alex")
  1. Write clear instructions in notes — what the twin should do, where to save output, what success looks like
  1. Move to ready
  1. Run openclaw workboard dispatch — the system claims the card and starts a subagent worker for that twin
  1. The twin executes, card moves to running → review when done
  1. Lumina reviews quality → done or blocked with feedback

Communication Flows

Lumina → Twins (task assignment)

  1. Create card on lumina-ops board, assigned to twin's agentId
  1. Move to ready
  1. Dispatch — twin receives the card context as a subagent task
  1. Twin executes and completes via workboard tools
  1. Lumina reviews → done

Twins → Lumina (requesting work)

Twins cannot create cards directly. They request through:

  • Telegram message to Roo (who tells Lumina)
  • Or via sessions_send to Lumina's main session
  • Lumina creates the card on their behalf

Lumina → Roo (escalation)

  1. Move card to blocked with reason
  1. Notify Roo via Telegram or webchat with: card title, what's blocked, what I need from him
  1. Once Roo responds, unblock → todo or running

Lumina → Self (nightly sweep)

During 2AM-6AM window:

  1. List all todo and scheduled cards on lumina-ops
  1. Execute each one:
  • Move to running
  • Do the work
  • Move to review → verify → done
  1. For recurring tasks, create next iteration
  1. Log the sweep in board/overnight-sweep-log.md
  1. Leave anything needing Roo as blocked with clear notes

Twin Learning Cycle (Weekly)

Recurring knowledge expansion managed through workboard, not cron:

Day Twin Task
Monday Alex Run 3 new NotebookLM queries on Alex 1-4
Tuesday Thiel Run 3 new queries on Thiel + Thiel 2 + strategy
Wednesday Collison Run 3 new queries on Collison + operations + engineering + ai-engineering
Thursday Pérez Run 2 new queries on Perez + cycle-research + governance
Friday Paul Run 2 new queries on Irish Wealth + Wealth Strategies + legal-tax

Flow:

  1. Sunday night: Lumina creates 5 cards (one per twin), scheduled for their day
  1. On the day: card moves to ready, dispatch sends it to the twin
  1. Twin picks their own questions based on current work gaps
  1. Twin runs queries, saves notes inside NotebookLM, writes brain note to vault
  1. Twin completes card with proof (note IDs, brain note path)
  1. Sunday: Lumina reviews all 5, marks done, creates next week's batch

Total: 13 queries/week — well within NotebookLM capacity.

Diagnostics I Watch

Signal Meaning Action
stranded_ready Card in ready/todo not updated in 1hr Check if blocked, dispatch or escalate
running_without_heartbeat Running card no update in 20min Check if worker died, reclaim or block
blocked_too_long Blocked card untouched for 24hr Escalate to Roo
repeated_failures 2+ failures on a card Investigate root cause, don't just retry
missing_proof Done card with no proof Add proof or downgrade to review
