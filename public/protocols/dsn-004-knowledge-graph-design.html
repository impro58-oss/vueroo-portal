← Back to Protocol Dashboard ﻿# DSN-004 Knowledge Graph Design Protocol

Department: DSN (Design) Version: 1.0 Created: 2026-05-25 Owner: Lumina Status: ACTIVE

Purpose

Design a knowledge graph for a domain — connecting concepts with typed relationships so that traversal produces better insights than flat-file search. Based on knowledge graph patterns from Building LLM Agents (Devlin).

Trigger

  • When a domain has enough concepts to benefit from structured relationships (typically 50+ concepts)
  • When flat-file search is returning poor results due to lack of context
  • When building Avaark's knowledge layer

    • Prerequisites

  • Domain clearly defined (e.g., "MedTech", "Trading", "Resonance")
  • Key concepts identified
  • Understanding of how concepts relate to each other

    • Steps

    Step 1: Identify Entities

    List all entities (nodes) in the domain:
  • Concrete entities: People, companies, products, devices, drugs, clinical trials
  • Abstract entities: Concepts, theories, frameworks, patterns, strategies
  • Process entities: Workflows, protocols, procedures

    • For each entity, define:

  • Type: What kind of entity is this? (Company, Drug, ClinicalTrial, Strategy, etc.)
  • Key attributes: What properties does it have?
  • Unique identifier: How do we reference it unambiguously?

    • Step 2: Define Relationships

    For each pair of entity types that connect, define:
  • Relationship type: (competes_with, treats, developed_by, part_of, contradicts, supports, etc.)
  • Direction: Is it one-way or bidirectional?
  • Strength: How strong is the connection? (strong/medium/weak)
  • Temporal: Is this connection permanent or time-limited?

    • Example relationship types for MedTech: 

    
Company --develops--> Device
Device --treats--> Condition
Company --competes_with--> Company
ClinicalTrial --tests--> Device
ClinicalTrial --shows--> Outcome
Condition --has_prevalence_of--> EpidemiologyData

    Step 3: Choose Storage

    For our current setup, the simplest approach:
  • Phase 1: JSON/Markdown files with explicit cross-references (what we have now, but structured)
  • Phase 2: Obsidian vault with wikilinks and graph view (leverages existing vault)
  • Phase 3: Graph database (Neo4j or similar) if scale demands it

    • Start with Phase 1. Don't over-engineer.

    Step 4: Build the Graph

    Create a schema document: 
    markdown

    Knowledge Graph: [Domain]
    Entity Types
    
| Type | Attributes | Examples |
|------|-----------|----------|
| Company | name, hq, revenue, products | Stryker, Medtronic |
| Device | name, type, clearance, indication | Pipeline Flex, Surpass |
| Condition | name, prevalence, geography | Intracranial aneurysm |
    Relationship Types
    
| From | Type | To | Strength | Example |
|------|------|----|----------|---------|
| Company | develops | Device | strong | Stryker develops Surpass |
| Device | treats | Condition | strong | Pipeline treats aneurysms |
| Company | competes_with | Company | medium | Stryker competes with Medtronic |
    Graph Statistics

    •

    Step 5: Populate

    For each entity in the domain: 1. Create an Obsidian note with proper tags (per vault tagger) 2. Add wikilinks [[EntityName]] to related entities 3. Ensure every relationship has a bidirectional link 4. Validate: every link resolves to an actual note

    Step 6: Query Patterns

    Define the questions the graph should answer:
  • "What devices compete with Pipeline Flex?" → Traverse: Device → competes_with → Device
  • "What conditions does the neurovascular market address?" → Traverse: Condition → treated_by → Device → developed_by → Company
  • "What clinical evidence supports flow diverters?" → Traverse: ClinicalTrial → tests → Device → treats → Condition

    • Step 7: Maintain

  • Schedule regular graph consistency checks (orphan nodes, broken links)
  • Update entities when new information arrives (per RSC-002, RSC-003)
  • Archive outdated relationships rather than deleting

    • Quality Gates

    Entity types defined with attributes
    Relationship types defined with direction and strength
    Storage approach chosen (Phase 1/2/3)
    Schema document created
    At least 20 entities populated with cross-links
    Query patterns defined and tested
    Maintenance schedule set
