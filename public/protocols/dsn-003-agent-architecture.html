DSN-003 Agent Architecture Protocol

Department: DSN (Design) Version: 1.0 Created: 2026-05-25 Owner: Lumina Status: ACTIVE

Purpose

Design an agent using the Agentic Mesh pattern. Every agent has identity, discovery, trust, transactions, and oversight. No agent is built without answering all five dimensions.

Trigger

  • Before building a new agent (pairs with DEV-001)
  • When redesigning an existing agent architecture
  • When evaluating whether to add capabilities to an existing agent

    • Prerequisites

  • Requirements document completed (DEV-001 Step 1)
  • Lethal Trifecta audit completed (DEV-006 Step 3)

    • Steps

    Step 1: Define Agent Identity

    markdown

    Agent Identity
    
Name: [unique agent name]
Version: [semver]
Purpose: [1-2 sentences — what it does]
Capabilities: [what it can do, specifically]
Limitations: [what it cannot do, specifically]
Department: [RSC/DEV/RPT/DSN/OPS/STR]
Protocols: [which protocols it follows]
Security Level: [LOW/MEDIUM/HIGH from DEV-006]
Human Oversight: [HITL — needs approval / HOTL — autonomous with monitoring]

    Step 2: Define Discovery

    How does this agent find what it needs?
  • Data sources: Where does it get input? (APIs, files, databases, web scraping)
  • Other agents: Does it need to coordinate with other agents? How?
  • Configuration: Where does it get its parameters? (config files, environment variables)
  • Scheduling: When does it run? (cron, on-demand, continuous)

    • Step 3: Define Trust

    How does this agent validate what it receives?
  • Input validation: What checks does it apply to incoming data?
  • Source verification: How does it know its data sources are trustworthy?
  • Error detection: How does it detect corrupted or wrong data?
  • Sanitization: Does it sanitize for NaN/undefined/missing values?

    • Step 4: Define Transactions

    What does this agent exchange with other systems?
  • Outputs: What does it produce? (JSON files, dashboards, messages, reports)
  • Consumers: Who uses its output? (Other agents, dashboards, Roo, external)
  • Format: What format are outputs in? (JSON, markdown, HTML, CSV)
  • Delivery: How does output reach consumers? (file system, HTTP, cron delivery, Telegram)
  • Frequency: How often does it produce output?

    • Step 5: Define Oversight

    Where does the human-in-the-loop sit?
  • HITL actions: What requires Roo's explicit approval? (external messages, financial transactions, deletions, security changes)
  • HOTL actions: What runs autonomously with monitoring? (data collection, memory consolidation, internal file management)
  • Escalation triggers: What automatically escalates to Roo? (high-confidence opportunities, critical errors, time-sensitive findings)
  • Logging: What gets logged? (All external calls, all financial decisions, all errors)
  • Health monitoring: How do we know it's working? (dashboard, health check, cron status)

    • Step 6: Design the Architecture

    Draw the agent's data flow: 
    
[Input Sources] → [Agent Core] → [Outputs]
                      ↕
               [State/Config]
                      ↕
               [Error Handling]
                      ↕
               [Logging/Monitoring]

    Specify:

  • Input format and validation rules
  • Core processing steps (numbered, like DEV-001)
  • Output format and delivery mechanism
  • State management (where does it save state between runs?)
  • Error handling (what happens when each step fails?)
  • Logging (what gets recorded and where?)

    • Step 7: Document

    Create the agent record in AGENTS.md and create a design doc in skills/[agent-name]/.

    Quality Gates

    Identity fully defined
    Discovery sources identified and accessible
    Trust validation rules specified
    Transactions clearly defined
    Oversight level set (HITL/HOTL)
    Architecture diagram drawn
    Agent registered in AGENTS.md
