TTE-001 Twin Team Expansion

Department: TTE (Twin Team Expansion) Status: NEW

Protocol: Twin Team Expansion (TTE-001)

Version: 1.0

Created: 2026-08-17

Owner: Roo

Gatekeeper: Lumina (bandwidth + feasibility review)

Applies to: All twin agents (Alex, Paul, Thiel, Pérez, Collison) operating on DreamQuest

Purpose

Twins can request permanent sub-agents to offload heavy lifting — copywriting, content creation, cold outreach, research, design, whatever role they need. But every permanent agent costs bandwidth (cron jobs, session storage, memory index, polling) and risks becoming dead weight if the role isn't justified.

This protocol ensures every team expansion is justified, reviewed, and approved before it consumes resources.

The Flow

Step 1: Twin Identifies Need

The twin recognizes a recurring workload pattern that justifies a permanent team member rather than ad-hoc subagent spawns. Signals:

  • Same type of task delegated 3+ times in a week
  • Core twin work (strategy, decisions, board duties) is being delayed by execution tasks
  • A clear role exists with repeatable responsibilities, not just a one-off project

Step 2: Twin Drafts Expansion Request

The twin writes a structured proposal to memory/twin-expansion-requests/ using this template:

# Expansion Request: [Role Name]

**Requested by:** [Twin name]
**Date:** [YYYY-MM-DD]
**Proposed agent ID:** [role]-[twin] (e.g., copywriter-alex)

## Role Definition
- **Title:** [e.g., Content Copywriter]
- **Mission:** [One sentence — what this agent exists to do]
- **Reports to:** [Twin name]
- **Workspace:** [Proposed workspace path]

## Justification
- **What recurring tasks will this agent own?** [List 3-5 specific tasks]
- **How much twin time does this free up?** [Estimate hours/week]
- **Why can't ad-hoc subagent spawns handle this?** [Explain why permanence is needed]
- **What happens if this agent doesn't exist?** [Consequence of not expanding]

## Workload Estimate
- **Expected cron jobs:** [N] (list them with schedule)
- **Expected sessions/day:** [N]
- **Expected model calls/day:** [N]
- **Peak concurrency impact:** [Low/Medium/High — explain]

## Deliverables
- **First 30 days:** [What this agent will produce in month 1]
- **Success metric:** [How we know this agent is earning its keep]
- **Kill criteria:** [What would trigger decommissioning — be honest]

## Proposed Configuration
- **Model:** [Primary + fallbacks]
- **Heartbeat:** [Frequency — keep minimal]
- **Cron jobs:** [List with schedules]
- **Telegram bot needed?** [Yes/No — if yes, name and purpose]
- **Memory/workspace:** [What files/directories it needs]

Step 3: Twin Sends Request to Roo + Lumina

The twin posts the request to Roo via Telegram (DM or Stockward group) with a brief summary:

> "I'm requesting a permanent [role] for my team. Full proposal at [path]. Can Lumina review for bandwidth?"

Step 4: Lumina Review (Gatekeeper)

Lumina reviews the proposal against these criteria:

Bandwidth Check:

  • Current system load (CPU, RAM, session count)
  • Current cron job count (target: under 70 active)
  • Memory index size impact
  • Concurrency headroom (max 9 concurrent, currently using N)

Dead Weight Check:

  • Does the justification show genuine recurring need?
  • Are the success metrics measurable?
  • Are the kill criteria specific enough to act on?
  • Is there a 30-day review built in?

Redundancy Check:

  • Does this role overlap with existing agents?
  • Could an existing agent absorb this work?
  • Is there a simpler solution (ad-hoc spawn, cron job, script)?

Cost Estimate:

  • Additional cron jobs: N
  • Additional sessions/day: N
  • Estimated memory index growth: N chunks/day
  • Risk level: Low/Medium/High

Lumina's Output:

## Lumina Review: [Role Name] for [Twin]

**Verdict:** [RECOMMEND APPROVE / RECOMMEND REJECT / NEEDS REVISION]
**Confidence:** [HIGH/MEDIUM/LOW]
**Date:** [YYYY-MM-DD]

### Bandwidth Assessment
- Current load: [CPU%, RAM%, cron count, session count]
- After expansion: [projected impact]
- Headroom: [remaining capacity]

### Feasibility
- [Observation 1]
- [Observation 2]
- [Observation 3]

### Red Flags (if any)
- [Flag 1]
- [Flag 2]

### Conditions (if approved)
- [Condition 1 — e.g., "30-day review mandatory"]
- [Condition 2 — e.g., "No Telegram bot until workload justifies it"]

### Recommendation
[2-3 sentences explaining the verdict]

Step 5: Roo Decision

Roo receives:

  1. The twin's proposal
  1. Lumina's review with recommendation

Roo makes the final call: Approve / Reject / Revise.

If approved, Lumina executes the setup:

  • Creates agent entry in openclaw.json
  • Creates workspace directory with SOUL.md, AGENTS.md
  • Configures any approved cron jobs
  • Wires Telegram bot if approved
  • Adds to tools.agentToAgent.allow list
  • Adds to agents.defaults.subagents.allowAgents list
  • Logs the expansion in memory/twin-expansion-requests/expansion-log.md

Step 6: 30-Day Review

After 30 days, Lumina automatically triggers a review:

  • Did the agent hit its success metrics?
  • Is it producing deliverables on schedule?
  • Is the kill criteria approaching?
  • Is the twin actually using it?

Outcomes:

  • ✅ Continue — agent is earning its keep
  • ⚠️ Revise — adjust scope, reduce cron frequency, or change role
  • 🔴 Decommission — kill criteria met or agent is dead weight. Remove from config, archive workspace, clean up cron jobs

Rules

  1. No silent spawns. Twins cannot create permanent agents without this flow. Ad-hoc subagent spawns for specific tasks are fine — permanent team members require approval.
  1. Lumina is gatekeeper, Roo is decision-maker. Lumina reviews and recommends. Roo decides. Always.
  1. Every permanent agent needs kill criteria. If you can't define when to decommission it, you can't have it.
  1. 30-day review is mandatory. No exceptions. If the agent isn't working, it goes.
  1. Bandwidth is the hard constraint. DreamQuest is an Intel N95 with 32GB RAM. It's not a datacenter. If Lumina says the bandwidth isn't there, the answer is no — regardless of how good the justification is.
  1. Dead weight is worse than no agent. An idle permanent agent costs cron slots, memory index space, and session storage. A decommissioned agent costs nothing. Err toward killing.
  1. Start small. New agents begin with minimal cron jobs (1-2 max) and no Telegram bot. Earn the extra infrastructure through demonstrated workload.
  1. One expansion at a time per twin. Don't request three team members simultaneously. Prove the first one works, then request the next.
