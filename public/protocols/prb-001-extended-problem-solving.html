PRB-001: Extended Problem Solving Protocol

Gap analysis system for multi-session problems — track Start, Middle, and End

Why This Exists: When you come back to the screen after a night's sleep and see 200 messages of heartbeats and error logs, the context of what we were working on is gone. This protocol ensures that never happens again. Every significant problem has a written Start, Middle, and End — so anyone (including future-you) can pick up exactly where things left off.

When to Apply

Apply this protocol when:

  • A problem will take more than one session to solve
  • A problem involves multiple iterations of research, testing, or refinement
  • The work involves routing to other models (DeepSeek, etc.) whose results need to be captured and tracked
  • The problem is complex enough that losing context would mean starting over
  • Roo says "this is a priority task" or "work on this over multiple sessions"

Do NOT apply for: Single-session tasks (quick fixes, simple queries, routine cron work).

Stage 1: START — Define the Problem

Do this ONCE, at the beginning. Write it to Obsidian.

Create a project document in the relevant project folder with this structure:

# [Project Name] — Gap Analysis & Status

**Created:** [date]
**Last Updated:** [date]
**Status:** ACTIVE / PAUSED / COMPLETE
**Priority:** 🔴 CRITICAL / 🟡 HIGH / 🟢 NORMAL

1.1 The Problem Statement

  • What exactly is the problem? (One clear sentence)
  • Why does it matter? (What does solving it unlock?)
  • What's the current baseline? (Numbers, not vibes)

1.2 Current State (START)

  • Where are we right now?
  • What's the metric we're measuring?
  • What's the random baseline / comparison point?

1.3 Target State (END)

  • What does success look like? (Specific, measurable)
  • What metric threshold means "done"?
  • What would regression look like? (What must NOT get worse)

1.4 Files & Code

  • Where does the code live?
  • Where are the results tracked?
  • Where is this document saved?

Stage 2: MIDDLE — Track Progress

Update this EVERY SESSION where work happens on this problem.

2.1 Session Log

## Session — [date]

**What was tried:** [approach name, one line]
**What changed:** [metric before → metric after]
**What was learned:** [insight, not just output]
**What's next:** [concrete next step]

2.2 Results Table

Maintain a running results table with every approach tested:

V11 baseline.........✅

2.3 Decisions Log

### Decision — [date]
**Decision:** [what was decided]
**Rationale:** [why, based on what data]
**Alternative considered:** [what else was on the table]
**Trade-off:** [what we gave up]

Stage 3: END — Close or Pivot

3.1 Closure

  • Did we hit the target? (Yes/No + numbers)
  • What was the final metric improvement?
  • What approach won?
  • What approaches failed and why?

3.2 Lessons Learned

  • What surprised us?
  • What did we waste time on?
  • What would we do differently?

3.3 Status Change

  • Change document status from ACTIVE → COMPLETE or ACTIVE → PAUSED
  • Update MEMORY.md to reflect the new status
  • If COMPLETE: archive learnings to memory/ and Obsidian

Route-to-Research Procedure

  1. Write the research brief IN the project document — don't rely on memory
  2. Include all current metrics in the brief — the model needs to know the baseline
  3. Specify the output file — where the research goes (always in memory/ with date prefix)
  4. Specify the output format — what sections, what depth, what decisions the research should inform
  5. When results arrive: read them, evaluate them, add to the results table, update the project document
  6. Never assume the research will be in context — it won't be. The project document IS the context.

Route-to-Implementation Procedure

  1. Read the project document first — don't start coding from memory
  2. Read the research file — understand what was proposed and why
  3. Create a new file (e.g., v11_2_pair_mining.py) — don't modify working code
  4. Backtest before integrating — run the new approach against 300+ draws
  5. Add results to the results table — no result = no progress
  6. Update the project document — session log, results, decisions
  7. Copy to Obsidian — the project document, the research, the backtest results

Context Rollover Rule

When context is getting full (past 80%):

  1. Run scripts/context-rollover.py to create a checkpoint
  2. The checkpoint links to the project document in Obsidian
  3. When resuming, read the project document FIRST — it has everything
  4. The project document IS the context. Everything else is cache.

Anti-Patterns

  • ❌ Don't start work without reading the project document. If one doesn't exist, create it first.
  • ❌ Don't assume the research brief is in memory. It was written in a session that may be gone.
  • ❌ Don't skip the results table. If you can't show before/after numbers, you can't show progress.
  • ❌ Don't declare a problem solved without hitting the target metric. "Improved" ≠ "solved."
  • ❌ Don't work on multiple approaches simultaneously. One at a time, test, record, decide.
  • ❌ Don't lose the thread. Every session that touches this problem MUST update the project document.
