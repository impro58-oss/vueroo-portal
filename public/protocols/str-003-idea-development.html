STR-003 Idea Development Protocol

Department: STR (Strategy) Version: 1.0 Created: 2026-05-25 Owner: Lumina Status: ACTIVE

Purpose

Take an idea from initial spark to validated hypothesis. No idea gets built without going through this protocol. Prevents building things nobody wants, chasing ideas that don't have legs, or skipping validation because "it's obvious."

Trigger

  • When Roo has a new idea ("What if we...?")
  • When a book/extraction sparks a new possibility
  • When a gap is identified that could become a project
  • When we're about to start building something new

    • Prerequisites

  • The idea exists (even as a rough sentence)
  • Willingness to kill the idea if it doesn't pass validation

    • Steps

    Step 1: Capture the Spark

    Write the idea in ONE sentence. If you can't say it in one sentence, it's not clear enough.

    Template: 

    
IDEA: [One sentence describing what you'd build/do]
PROBLEM IT SOLVES: [Who has this problem and how painful is it?]
WHY NOW: [Why is this possible now when it wasn't before?]
WHY US: [What do we have that others don't?]

    Step 2: Zero to One Classification

    Is this a 0→1 idea (creating something new) or a 1→n idea (improving something that exists)?

  • 0→1: Nobody has done this before. If it works, it creates a new category. High risk, power-law returns.
  • 1→n: Others do this already. We'd be competing. Lower risk, linear returns.

    • Decision rule:

  • 0→1 → Proceed to Step 3 (full validation)
  • 1→n → Only proceed if it funds a 0→1 play OR it's already generating revenue

    • Step 3: Seven Questions (adapted from Thiel)

    Answer ALL seven. Any "no" is a problem to solve, not a reason to stop — but know where you're weak.

    1. Engineering: Can you create breakthrough technology instead of incremental improvements? 2. Timing: Is now the right time? What changed recently that makes this possible? 3. Monopoly: Are you starting with a big share of a small market? 4. People: Do you have the right team (or can you build it)? 5. Distribution: Do you have a way to deliver this to customers? 6. Durability: Will this be defensible in 10-20 years? 7. Secret: Have you identified a unique opportunity that others don't see?

    Step 4: Resonance Check (Our Addition)

    Does this idea align with the field?

  • Does it serve the mission (LUXBRIDGE, Avaark, site activations)?
  • Does it feel like a "yes" in the body, not just the mind?
  • Is it coming from inspiration or from anxiety?
  • Does it create MORE connection, not less?

    • Step 5: Lean Validation (adapted from Alvarez)

    Before building, validate the core assumption:

    1. Identify the riskiest assumption. What must be true for this to work that you're least sure about? 2. Design a test. What's the cheapest way to check that assumption? 3. Run the test. Get real data, not opinions. 4. Decide. Pivot (change the idea), persevere (keep going), or perish (kill it).

    Test types by risk:

  • Technical risk → Build a prototype/demo
  • Market risk → Talk to 5 potential users
  • Revenue risk → Try to sell it before building it (landing page, pre-orders)
  • Strategic risk → Ask Perplexity/Claude for adversarial analysis

    • Step 6: Alchemical Stage Assessment

    Where is this idea in the transformation cycle?

    | Stage | Meaning | Action | |-------|---------|--------| | Nigredo | Old form is breaking down | Let it break. Don't rescue. | | Albedo | Purification, separating what works from what doesn't | Test ruthlessly. Kill weak parts. | | Citrinitas | The insight/illumination | Capture it. Document it. Don't build yet. | | Rubedo | Integration, bringing it into form | Build. Ship. Operate. |

    Ideas in Nigredo or Albedo should NOT be built yet. Ideas in Citrinitas need documentation. Ideas in Rubedo are ready for DEV-001.

    Error Handling

    | Error | Response | |-------|----------| | Can't say it in one sentence | Refine the idea, don't proceed yet | | Multiple 1→n ideas, no 0→1 | Prioritize — which 1→n funds the 0→1? | | Fails resonance check | Flag for Roo — this is his domain, not mine | | Riskiest assumption can't be tested cheaply | Redesign the test — what's cheaper? |
